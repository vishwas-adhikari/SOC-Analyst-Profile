# 📘 SOC Analyst Handbook: Web Server Log Analysis

**Category:** Web Forensics / Incident Response
**Severity:** Core Skill
**Skill Level:** Intermediate

---

### 1. The Concept

**The Analogy (ELI5)**
*   **WAF Log:** The Security Guard's report. "I stopped a guy with a knife at the door." (Shows Intent).
*   **Web Server Log:** The Bartender's receipt. "I served Table 4 a drink at 9:00 PM." (Shows Reality).
*   *Why we need it:* If the Guard (WAF) was sleeping or didn't see the knife, the Bartender's receipt is the only proof that the attacker actually got inside and ordered something malicious.

**The Technical Definition**
Web Log Analysis involves reviewing the access logs generated by web servers (Apache, Nginx, IIS). Unlike WAF logs which show blocked attempts, Web Logs typically show **successful connections**. They are the definitive source of truth for determining if an attack executed successfully.

---

### 2. Log Anatomy (The Vocabulary)

Most servers use the **Combined Log Format**. You must be able to read this raw string.

#### **📝 Common Log Fields**

| Field | Example | SOC Interpretation |
| :--- | :--- | :--- |
| **Source IP** | `71.16.45.142` | The attacker's IP. |
| **Timestamp** | `[12/Dec/2021:09:24:42]` | Crucial for correlating with WAF/Database logs. |
| **Method** | `GET`, `POST`, `HEAD` | **GET**: Log contains the payload (visible). **POST**: Payload is in the body (usually **NOT** logged). |
| **URL / URI** | `/?id=SELECT...` | The target file and the malicious parameters. |
| **Status Code** | `200`, `404`, `500` | The Verdict. Did the server accept the malicious input? |
| **Bytes** | `486`, `13539` | Response Size. **Huge spike = Data Exfiltration.** |
| **User-Agent** | `curl/7.72.0` | The tool used. Browsers say "Mozilla..."; Scripts say "Python", "Curl", or "Java". |

---

### 3. Example Log (The Evidence)

**Raw Apache/Nginx Log:**
```text
192.168.8.54 - - [29/Jun/2022:07:42:48] "GET /bwapp/sqli_1.php?title=%25iron%27+union+select+1%2Cuser%28%29--+ HTTP/1.1" 200 13539 "-" "Mozilla/5.0... Chrome/102.0"
```

**Breakdown & Analysis:**
1.  **Attacker:** `192.168.8.54`.
2.  **Attack:** SQL Injection (`union select user()`).
3.  **Method:** `GET` (We can see the attack in the URL).
4.  **Response:** `200 OK`. **The server accepted it.**
5.  **Size:** `13539` bytes.
    *   *Analysis:* A normal search might return 500 bytes. A return of 13,000 bytes suggests the database dumped a lot of data. **Successful Breach.**

---

### 4. HTTP Status Codes (The Detective's Guide)

In Web Logs, the status code tells you the outcome of the attack.

| Code | Meaning | SOC Scenario |
| :--- | :--- | :--- |
| **200 (OK)** | Success | **Danger.** If the URL contains an exploit, the server ran it. |
| **301/302** | Redirect | Check the `Location` header (if captured). Did it redirect to `/admin` (Bad) or `/login` (Good)? |
| **403 (Forbidden)** | Access Denied | **Safe.** Permission settings blocked the attacker. |
| **404 (Not Found)** | Not Found | **Scanning.** Attacker is guessing file names (`/admin.php`, `/backup.zip`). |
| **500 (Error)** | Server Error | **Partial Success/DoS.** The exploit crashed the app or caused a DB syntax error. |

---

### 5. Detection Patterns & Anomalies

**1. The "POST" Blind Spot**
*   **Fact:** Web servers default to logging the URL, not the Body.
*   **Scenario:** `POST /login.php HTTP/1.1 200 OK`.
*   **Problem:** You cannot see if they sent `user=admin&pass=123` or `user=admin&pass=' OR 1=1`.
*   **Detection:** Look for High Volume of POSTs (Brute Force) or 500 Errors (SQLi attempt crashing the login).

**2. User-Agent Analysis**
*   **Pattern:** `User-Agent: sqlmap/1.4` or `User-Agent: python-requests/2.2`.
*   **Meaning:** Automated tools. Real users don't browse with Python.

**3. The "Method" Mismatch**
*   **Pattern:** `PUT /uploads/shell.php` or `DELETE /logs/access.log`.
*   **Meaning:** Attackers trying to upload backdoors or delete evidence.

**4. Frequency Analysis (Scanning)**
*   **Pattern:** One IP generating 500 requests per minute with `404` codes.
*   **Meaning:** Directory Busting (Gobuster/Dirb) looking for hidden files.

---

### 🌳 6. Mini Decision Tree (Triage Logic)

*   **🟢 Low Priority (Scanner)**
    *   `Status: 404/403` + `UA: Nessus/OpenVAS`
    *   *Action:* Ignore. Failed scan.

*   **🟡 Medium Priority (SQLi Error)**
    *   `URI: UNION SELECT` + `Status: 500 Internal Error`
    *   *Action:* Attack failed but caused instability. Check WAF why it wasn't blocked.

*   **🔴 High Priority (Web Shell Upload)**
    *   `Method: POST` + `File: .php/.jsp` + `Status: 200/201` + `Path: /images/`
    *   *Action:* **Isolate Host.** Attacker likely uploaded a shell to an image folder.

*   **🟣 Critical Priority (Data Exfil)**
    *   `URI: /database/export` + `Status: 200` + `Bytes: 500MB`
    *   *Action:* **Major Incident.** Huge data download.

---

### 🛠️ 7. Investigation Playbook

1.  **Decode the Request:** URL-encoded strings (`%27`, `%20`) are unreadable. Decode them to see the SQLi/XSS payload.
2.  **Baselinse the Size:** What is the normal byte size for this page? If normal is 2KB and this request is 50MB, it's exfiltration.
3.  **Check the Timeline:** Did they scan first (`404s`) -> find a vulnerability (`500s`) -> and finally succeed (`200 OK`)?
4.  **Pivot:** Take the Source IP -> Check Firewall Logs (did they connect to other ports?) -> Check Threat Intel.

---

### 10. Interview Summary (TL;DR)
*   **WAF vs Web Logs:** WAF shows what was *attempted* (and maybe blocked); Web Logs show what *happened*.
*   **Blind Spot:** `POST` request bodies are rarely logged. You won't see the password or payload in a standard log.
*   **Key Fields:** `Status Code` (200 vs 404), `Method` (GET vs POST), `Response Size` (Bytes).
*   **The "200" Trap:** A 200 OK code on a malicious URL (`.../shell.php`) confirms the compromise.
*   **User-Agent:** The easiest way to spot automated scanners vs. real humans.
