# 📘 SOC Analyst Handbook: Firewall Log Analysis (Practical)

**Category:** Network Forensics / Log Analysis
**Severity:** Core Skill (Required for every investigation)
**Skill Level:** Intermediate

---

### 1. The Concept

**The Analogy (ELI5)**
*   **Packet Filtering (Layer 3):** The mailroom clerk checks the address on the envelope. If it's addressed to "HR Department," it goes through. He doesn't open it.
*   **NGFW (Layer 7):** The clerk opens the envelope. He sees that even though it's addressed to HR, the letter inside is written in "SSH Language" (not English). Since HR shouldn't receive SSH, he shreds it.

**The Technical Definition**
Firewall Log Analysis involves interpreting the records generated by network edge devices. Modern **Next-Generation Firewalls (NGFW)** provide "Application Awareness," meaning logs don't just show `Port 80`, they show the specific service (e.g., `Facebook-Chat`, `BitTorrent`, `HTTPS`).
*   **Key Goal:** Determine if traffic was **Allowed** (successful connection) or **Denied** (blocked attempt).

---

### 2. Log Anatomy (The Vocabulary)

Understanding the specific fields in a raw log is the first step to analysis. Below are the standard fields you will see (based on Fortinet/Cisco formats).

#### **📝 Common Log Fields**

| Field | Definition | Why it matters for SOC |
| :--- | :--- | :--- |
| **srcip / dstip** | Source & Destination IP | Who is talking to whom? |
| **srcport / dstport** | Source & Destination Port | What "door" are they trying to open? (e.g., 443 = Web, 22 = SSH). |
| **service / app** | Application Name | The *actual* traffic type (e.g., `BitTorrent`, `Tor`), regardless of the port used. |
| **sentbyte** | Bytes Sent (Upload) | High numbers here indicate **Data Exfiltration** or file uploads. |
| **rcvdbyte** | Bytes Received (Download) | High numbers here indicate file downloads. |
| **duration** | Time Elapsed | Long durations (e.g., 3600s) indicate **Tunneling** or remote access sessions. |
| **policyid** | Rule ID | Which firewall rule allowed/blocked this? (Helps find misconfigurations). |
| **transip** | Translated IP (NAT) | The Public IP the traffic used when leaving your network. |

#### **🚦 Firewall Actions (The Verdict)**

This is the most critical field. It tells you the outcome of the connection.

| Action | Meaning | SOC Interpretation |
| :--- | :--- | :--- |
| **Accept / Allow** | **Success.** The packet passed through the firewall. | Investigate the *content* (Bytes/Duration). If the destination is malicious, you have a breach. |
| **Deny** | **Blocked (Loud).** The packet was stopped, and a notification (ICMP Unreachable) was sent back to the sender. | The firewall did its job. Usually creates "noise" from scanners. |
| **Drop** | **Blocked (Silent).** The packet was stopped, and *no* response was sent. The sender just sees a timeout. | Preferred for external interfaces to slow down attackers. |
| **Close** | **Session End.** The communication finished normally. | Use this to calculate the total duration of a session. |
| **Client-RST** | **Client Reset.** The *user* killed the connection. | Could be a user closing a tab, or malware aborting a connection to hide. |
| **Server-RST** | **Server Reset.** The *server* killed the connection. | The server might be down, or the exploit crashed the service. |

### 3. Example Log (The Evidence)

**Raw Fortinet Log:**
```text
date=2022-05-21 time=14:06:38 devname="FG500" type="traffic" srcip=172.14.14.26 srcport=50495 dstip=142.250.186.142 dstport=443 action="accept" service="HTTPS" sentbyte=2518 rcvdbyte=49503 srccountry="Reserved" dstcountry="United States" transip=89.145.185.195
```

**Breakdown & Analysis:**
1.  **Who:** `172.14.14.26` (Internal LAN IP).
2.  **Where:** `142.250.186.142` (Google, United States).
3.  **What:** `HTTPS` (Port 443).
4.  **Verdict:** `accept` (Traffic was allowed).
5.  **Data:** `Sent: 2.5KB`, `Received: 49KB`.
    *   *Interpretation:* This looks like a normal web browsing session (Downloading a small web page).

### 4. Detection Tricks & Patterns

**1. Port Scanning (Reconnaissance)**
*   **Pattern:** Single `srcip` -> Multiple `dstport` (21, 22, 23, 80, 443) -> Action `Deny/Drop`.
*   *Meaning:* An attacker is rattling the doorknobs to see what is unlocked.

**2. Data Exfiltration**
*   **Pattern:** `Action: Accept` + `sentbyte` is huge (e.g., 5GB) + `rcvdbyte` is small.
*   *Meaning:* An internal host uploaded massive data to an external IP.

**3. Lateral Movement (LAN-to-LAN)**
*   **Pattern:** `srcintf="LAN"` -> `dstintf="LAN"`.
*   *Meaning:* Traffic moving *sideways* inside the network. This is suspicious if it involves Admin ports (RDP/SSH) between workstations.

**4. The "Check-In" (Beaconing)**
*   **Pattern:** Periodic `Accept` logs every 60 seconds to a low-reputation IP with small byte sizes.
*   *Meaning:* Malware checking with a C2 server for commands.

---

### ⚠️ 5. Signal vs. Noise (Critical Thinking)

| Observation | ✅ Benign (False Positive) | ❌ Malicious (True Positive) |
| :--- | :--- | :--- |
| **Inbound Deny** | The Internet scanning you (Background noise). | Targeted scan from a specific IP followed by a successful connection. |
| **High Outbound Bytes** | Backup to Cloud (AWS/Azure), Video Call. | Upload to `Mega.nz`, `Pastebin`, or unknown IP. |
| **Client-RST** | User closed browser while page was loading. | Malware abruptly terminating connection after sending payload. |
| **Traffic to "Risky" Country** | Business partner or traveling employee. | No business justification + Server traffic. |

### 6. Investigation Steps (The Playbook)

**Step 1: Check the Action**
*   If `Deny/Drop`: The firewall stopped it. Monitor to see if they try a different method.
*   If `Accept`: The traffic passed. You must investigate the *content* (using Proxy or NetFlow logs).

**Step 2: Check the Direction**
*   **Inbound:** Did an external IP hit a public server? (Normal). Did they hit an internal workstation? (Critical).
*   **Outbound:** Did an internal server connect to a known bad IP? (Indicator of Compromise).

**Step 3: Correlation (The Pivot)**
*   *Scenario:* You see an allowed connection to a suspicious IP.
*   *Pivot:* Check **Antivirus/EDR logs** for that internal host at that specific time. Did a malicious process run?
*   *Pivot:* Check **IPS logs**. Did the IPS see the *payload* of that packet and identify an exploit?

---

### 📊 7. Impact Assessment

**1. Data at Risk**
*   Check `sentbyte`. If it's small (<1KB), likely just C2 instructions. If it's large (>50MB), files were likely stolen.

**2. Blast Radius**
*   Is the Source IP a single laptop? Or is it the Domain Controller?
*   If the DC is communicating outbound to a malicious IP, the entire network is compromised.

**3. Urgency**
*   **Outbound C2 (Accept):** Immediate Containment.
*   **Inbound Scan (Deny):** Low Urgency (Monitor).

### 9. Interview Summary (TL;DR)
*   **Action Types:** `Accept` (Allowed), `Deny` (Blocked + Notification), `Drop` (Blocked Silently).
*   **NGFW Value:** Can see "Applications" (e.g., Skype) not just "Ports" (e.g., Port 80).
*   **Key Fields:** Always look at `sentbyte` vs `rcvdbyte` to distinguish Downloads vs Uploads (Exfiltration).
*   **Analysis Logic:** Start with `Action`. If allowed, check `Direction` and `Bytes`. Correlate with Endpoint logs to find the process responsible.
